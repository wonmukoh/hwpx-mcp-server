# 01. 왜 다시 만드나

지금 쓰는 MCP 를 며칠 붙들고 고쳤다. 열일곱 차례. 그 기록이
[`MCP/hwpx-mcp-작업/작업일지.md`](../../MCP/hwpx-mcp-작업/작업일지.md) 에 있다.

고친 것은 **전부** 같은 모양이었다.

> 도구는 "성공했습니다" 라고 답한다. 파일에도 흔적이 남는다.
> **그런데 한글 화면에는 안 나온다.**

이런 버그는 XML 검사를 통과한다. 시험도 통과한다.
PDF 로 뽑아 눈으로 보기 전에는 아무도 모른다.

---

## 뿌리 다섯

### 1. XML 을 문자열로 수술한다

`HwpxDocument.ts` 는 **567KB 한 파일**이다. XML 을 정규식으로 찾아 문자열을 갈아 끼운다.

여기서 나온 버그들:

| 버그 | 정체 |
|---|---|
| 그림이 표 안으로 들어감 | `<hp:p>` 정규식이 `<hp:pic>` 을 물었다 |
| 각주 검사가 늘 통과 | `<hp:footNote>` 검사가 `<hp:footNotePr>`(설정)에 걸렸다 |
| 미주가 각주 속으로 | 문단 끝을 '첫 번째 `</hp:p>`' 로 잡았다. 각주 안의 문단이 걸린다 |
| 표가 표 안으로 | 태그 깊이를 셀 때 이름 경계를 안 봤다 |

경계를 확인하는 헬퍼(`indexOfOpenTag`)를 만들어 **18군데**를 고쳤다.
그런데 그건 증상 처리다. 다음에 정규식을 하나 더 쓰면 또 물린다.

**파싱해서 트리로 다루면 이 부류가 통째로 사라진다.**

### 2. 대기열이 26개다

`_pendingCellStyles`, `_pendingTableInserts`, `_pendingImageInserts`, …
저장할 때 순서대로 적용한다. 그런데 **순서가 중요하다.**

- 표 병합은 셀 꾸미기보다 먼저 (좌표가 바뀐다)
- 부분 서식은 전체 서식보다 나중 (안 그러면 덮인다)
- 표 높이 맞춤은 내용이 다 들어간 뒤

이 순서가 `save()` 안에 손으로 나열돼 있다. 큐를 하나 더하면 어디에 끼울지
사람이 판단해야 한다. **어디에 끼워야 하는지 코드가 말해 주지 않는다.**

### 3. 위치를 번호로 가리킨다

`after_index: 5` 로 넣는다. 그런데

- 표지 제목은 요소를 **3개** 늘린다
- 개조식 목록은 **줄 수만큼** 늘린다
- 표는 **1개**로 센다 (표를 감싼 문단이 곧 그 표다)

부르는 쪽이 셀 수 없다. 나도 세 번 틀렸다. 틀리면 **조용히 엉뚱한 데 들어간다.**

범위 밖 번호를 주는 편법(`99999`)도 안 통했다. 큐마다 다르게 해석해서 순서가 뒤섞였다.

결국 `compose_document` 를 만들어 번호를 안쪽에 숨겼다. 그건 우회지 해결이 아니다.

### 4. 모델과 파일이 따로 논다

메모리 모델(`_content.sections`)과 파일(zip 안 XML)이 따로 있고,
저장할 때 맞춘다. 그래서 **모델만 바뀌고 파일에는 안 써지는** 도구가 있었다.

감사해 보니 **21개**였다. 전부 "성공했습니다" 라고 답하고 있었다.

### 5. 도구가 100개가 넘고 이름이 제각각이다

```
insert_table_row     after_row
insert_table_column  after_col
delete_table_row     row_index
delete_table_column  col_index
```

같은 뜻인데 이름이 넷이다. 오늘 이걸로 세 번 틀렸다.
사람인 내가 틀렸다면 모델은 더 틀린다.

도구가 많으면 모델이 고르는 정확도도 떨어진다. Codex·Gemini 는 특히 그렇다.

## 고쳐서 알아낸 것 — 이건 전부 가져간다

코드는 안 가져가지만 **알아낸 사실**은 값어치가 크다.
전부 한글로 기준 파일을 만들어 바이트 단위로 비교해 얻은 것이다.

| 사실 | 어떻게 알았나 |
|---|---|
| 한글은 **압축된 BinData 를 안 읽는다** (STORE 로 넣어야 그림이 보인다) | 한글이 만든 파일과 압축 방식만 달랐다 |
| 머리말·꼬리말·각주·쪽번호·다단은 전부 **문단 안 `<hp:ctrl>` 컨트롤** | secPr 자식으로 넣었더니 통째로 무시됐다 |
| `</hp:secPr>` 다음은 **`colPr` 자리** — 그 앞에 끼우면 구역 속성이 죽는다 | 머리말을 넣으니 쪽 테두리가 사라졌다 |
| 한글은 **표 높이를 다시 계산하지 않는다** | 왕복 저장시켜도 높이가 그대로였다 |
| 표 안 줄 간격 = 글자 크기 × **1.6**, 한 줄짜리 칸은 글자 크기만 | 한글이 그린 PDF 를 pdfplumber 로 자로 쟀다 |
| 각주 본문에 `<hp:autoNum>` 이 없으면 각주를 통째로 버린다 | 한글로 각주를 단 파일과 비교했다 |
| 쪽 테두리 '모든 쪽' 은 BOTH·ODD·EVEN 셋 다 써야 한다 | BOTH 만 바꾸니 ODD/EVEN 의 '없음' 이 이겼다 |
| 목록에 없는 글꼴은 조용히 0번으로 떨어진다 | 글꼴을 바꿔도 안 바뀌었다 |
| 한글은 PDF 로 링크를 안 내보낸다 | **검증 기준이 틀렸다.** 왕복 저장으로 바꿔서 확인했다 |
| 표 기하: 셀 폭 = 덮는 열 폭의 합, **높이는 규칙이 아니다** | 실제 문서 479개 표 실측 |
| HWPUNIT: **1pt = 100**, 1mm = 283.465 | — |

### 정부 문서에 대해 알아낸 것 — 그리고 한 번 틀렸다

처음에 교육부 업무계획 **한 편**의 태그를 세고 이렇게 적었다.

```
tbl 27   pic 1   line 0   rect 0   ellipse 0   polygon 0   chart 0
```

"도형이 하나도 없다. 정부 문서의 시각 디자인은 표와 조판이 전부다."

**틀렸다.** 0단계에서 실제 문서 113편을 세어 보니:

```
tbl 110   pic 33   pageNum 33   rect 24   container 13
pageHiding 12   header 6   line 4   ellipse 2   polygon 1
```

`rect` 가 **24편**에 있고 한 편에는 **74개**다. 교육부 기본계획에는 **수식**도 있다.
표본 한 편이 예외였던 것이다.

맞았던 것: **표는 거의 모든 문서에 있다** (110/113). 표가 중심이라는 판단은 옳았다.
새로 안 것: **`pageHiding`(첫 쪽 감추기)이 12편** — 생각보다 흔하다.
             **각주는 1편뿐** — 우선순위를 낮춰도 된다.

> 표본 하나로 일반화하지 않는다. 이것도 이 프로젝트의 규칙이 됐다.

## 그래서 무엇을 바꾸나

| 지금 | 새로 |
|---|---|
| 정규식으로 XML 수술 | 파싱 → 트리 → 직렬화 |
| 대기열 26개, 순서는 손으로 | 연산 로그 하나, 순서는 연산이 선언 |
| 위치를 번호로 | 안정 ID |
| 모델과 파일 따로 | 하나의 모델. 저장은 직렬화일 뿐 |
| 도구 100개+, 이름 제각각 | 30개 안쪽, 이름 규칙 하나 |
| 검증은 XML 검사 | 규격·왕복·시각 삼중 |

자세한 것은 [`02-설계.md`](02-설계.md).

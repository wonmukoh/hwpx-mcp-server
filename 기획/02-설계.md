# 02. 설계

---

## 설계 원칙 여섯

### 원칙 1 — XML 은 트리다

읽기 → 모델 → 쓰기. 문자열 수술은 없다.

모르는 요소·속성은 **원형 그대로 보존한다**(round-trip fidelity).
남의 문서를 열어 한 글자만 고치고 저장했을 때 나머지가 바뀌면 안 된다.
이것이 지켜지는지는 **왕복 검사**로 기계가 확인한다 ([`05-검증.md`](05-검증.md)).

### 원칙 2 — 연산은 순수 함수다

```
연산(문서) → 결과<문서, 실패이유>
```

- 부수 효과가 없다. 시험하기 쉽다.
- 실패하면 문서를 안 바꾸고 **왜** 를 말한다.
- 순서 의존은 연산이 **스스로 선언한다** (`after: ['표병합']` 같은 식).
  사람이 `save()` 안에서 순서를 외우지 않는다.

### 원칙 3 — 가리킬 땐 ID 로

모든 요소에 안정 ID 가 있다. 삽입해도 안 밀린다.
번호(`index`)는 **조회 결과에 붙어 나오는 정보**지 지시 수단이 아니다.

만든 도구는 만든 것의 ID 를 돌려준다.

### 원칙 4 — 조판이 1급이다

문서를 새로 쓰는 일은 **블록을 선언하는 것**이 기본 경로다.
낱개 편집은 그 위에 얹는다. 반대가 아니다.

지금 MCP 에서 `compose_document` 를 나중에 얹었더니 아래층과 겹치는 코드가 생겼다.
처음부터 조판을 아래에 두면 안 겹친다.

### 원칙 5 — 스타일은 복제해서 고친다

`charPr` / `paraPr` / `borderFill` 을 **새로 만들지 않는다.**
지금 쓰는 것을 복제해 요청분만 덮어쓰고, 같은 모양이 이미 있으면 그걸 쓴다.

- 새로 만들면 한글이 안 읽거나 문서 모양이 통째로 바뀐다
- 지문(fingerprint)으로 중복을 없애야 header 가 안 부푼다
- `itemCnt` 는 항상 **실제 개수**와 맞춘다 (안 맞으면 한글이 목록을 잘라 읽는다)

### 원칙 6 — 못 하면 못 한다고 한다

[`작성지침.md`](../작성지침.md) 1항. 여기서는 **타입으로 강제한다.**

```ts
type 결과<T> = { ok: true; value: T } | { ok: false; 이유: string; 어떻게: string };
```

`void` 를 돌려주는 연산은 없다.

## 계층

```
┌─ server ────────── MCP 도구 표면. 스키마·구조화 출력·오류
├─ compose ───────── 블록 → 연산.  제목·띠·개조식·표·그림
├─ doc ───────────── 문서 모델. 안정 ID, 연산 로그, 스타일 확보
├─ hwpx ─────────── 컨테이너. zip, 부품, manifest, 무결성
└─ owpml ────────── 규격. 타입, 파서, 직렬화기, 단위
```

**아래가 위를 모른다.** `owpml` 은 MCP 를 모르고, `doc` 은 조판을 모른다.

### owpml — 규격

- OWPML(KS X 6101) 요소를 타입으로. 모르는 것은 `Unknown` 으로 **보존**한다.
- 파서와 직렬화기. **왕복 무손실**이 이 계층의 유일한 합격 기준이다.
- 단위: `pt`, `mm`, `HWPUNIT` 를 타입으로 구분한다.
  섞어 쓰다 틀리는 일이 잦았다 (1pt = 100 HWPUNIT, 1mm = 283.465).

```ts
type HwpUnit = number & { readonly __hwpunit: unique symbol };
const pt = (v: number): HwpUnit => Math.round(v * 100) as HwpUnit;
```

### hwpx — 컨테이너

- zip 부품: `mimetype`(무압축) / `version.xml` / `settings.xml` / `META-INF/*` /
  `Contents/{header.xml, section*.xml, content.hpf}` / `BinData/*`
- **BinData 압축은 형식을 따른다.** 처음엔 "한글이 압축된 BinData 를 안 읽는다"고 적었는데
  2단계에서 세어 보고 뒤집었다. 진짜 규칙은 **이미 압축된 형식은 그냥 담고, 아닌 것은 압축한다**:
  jpg 57건·png 41건 전부 STORE / bmp 26건·wmf 1건 전부 DEFLATE. 이건 이 계층이 강제한다.
- manifest(`content.hpf`) 와 실제 파일이 어긋나지 않게 한 곳에서 관리한다.

### doc — 문서 모델

- 요소마다 안정 ID
- 연산 로그. 적용은 로그를 순서대로 접는 것
- 스타일 확보(`ensure*`): 복제 → 패치 → 지문 대조 → 재사용 또는 추가
- 표 기하: 폭은 규칙(셀 폭 = 덮는 열 폭의 합), 높이는 규칙이 아니다.
  다만 **우리가 만든 표는 높이를 계산해 넣는다** (한글이 안 해 준다)

### compose — 조판

블록을 연산으로 바꾼다. 블록 종류는 [`04-도구-설계.md`](04-도구-설계.md).
정부 문서에서 실제로 쓰이는 것만 만든다.

> 처음엔 "도형은 안 만든다"고 적었다. 교육부 문서 **한 편**을 보고 내린 판단이었다.
> 113편을 세어 보니 `rect` 가 24편(한 편은 74개), `line` 4편, `ellipse` 2편,
> `polygon`·`connectLine` 각 1편, `container` 13편, 거기에 `equation` 까지 있었다.
> **도형은 만든다.** — 표본 한 편으로 일반화하지 않는다는 규칙이 여기서 나왔다.

### server — MCP

[`03-MCP-규격과-범용성.md`](03-MCP-규격과-범용성.md).

## 런타임과 배포

**TypeScript + Node 20+**

| 왜 | |
|---|---|
| MCP SDK 가 가장 성숙하다 | 규격 변화를 따라가기 쉽다 |
| `npx` 로 설치 없이 실행 | 세 클라이언트 모두 이 방식을 쓴다 |
| 기존 자산 재사용 | 알아낸 사실을 옮기기 쉽다 |
| zip·XML 생태계 | jszip, 파서 선택지 |

배포:

```jsonc
// 어느 클라이언트든 같은 모양
{ "command": "npx", "args": ["-y", "hwpx-mcp"] }
```

한글 COM 자동화(검증용)는 **Windows 에서만** 동작한다.
그건 개발·검증 도구지 서버 기능이 아니다. **서버 자체는 한글 없이 돌아간다.**

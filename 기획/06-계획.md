### 1단계 — `owpml` (규격 계층) ✅ 끝

**합격 기준을 넘겼다.**

| | |
|---|---|
| 왕복 무손실 | **문서 113편 / XML 부품 802개 / 3,590만 글자 — 실패 0** |
| 속도 | 0.9초 (초당 4,170만 글자) |
| 시험 | 62개 통과 |
| 소스 | 875줄 |

#### 어떻게 무손실을 만들었나

보통 XML 파서로는 안 된다. 속성 순서·자기닫음 표기(`<a/>` vs `<a></a>`)·공백·
`&#xA;` 같은 문자 표기를 다 잃는다.

그래서 **노드마다 원본에서의 자리(start~end)를 들고 있게** 했다.
직렬화할 때 **손대지 않은 노드는 원본 조각을 그대로 뱉는다.**
고친 노드만 새로 쓴다. 무손실이 성질로 보장된다 — 애써 맞추는 게 아니다.

```
안 고친 노드  →  source.slice(start, end)     원본 그대로
고친 노드     →  다시 조립                     그 자리만
```
#### 만든 것

| 파일 | 하는 일 |
|---|---|
| `xml/ast.ts` | 나무 모양. 원본 자리와 `dirty` 표시 |
| `xml/parse.ts` | 파서. **아무것도 해석하지 않는다** (이스케이프도 안 푼다) |
| `xml/serialize.ts` | 직렬화. 안 고친 것은 원본 조각 |
| `xml/edit.ts` | **고치는 유일한 통로.** 여기를 지나면 `dirty` 를 잊을 수 없다 |
| `xml/query.ts` | 찾기. 정규식이 아니라 나무를 훑는다 |
| `units.ts` | `Pt`/`Mm`/`HwpUnit` 를 **타입으로 구분**. 섞으면 컴파일이 안 된다 |

#### 검사가 고장을 잡는지 확인했다

왕복이 첫 시도에 통과했다. 그럴수록 의심해야 한다 —
파서가 아무 일도 안 하고 원본을 뱉어도 왕복은 통과한다.

그래서 확인했다:
- 파서가 진짜 나무를 만드나 (요소 50+, 깊이 5+, 표 셀 9개를 세어 봤다)
- **일부러 고장 냈을 때 검사가 실패하나** — 속성 순서 바꾸기, 자기닫음 풀기,
  이스케이프 풀기, 공백 다듬기. 넷 다 잡힌다
- 고친 자리만 바뀌나 — 속성 하나를 바꿔도 옆의 홑따옴표와 공백은 그대로다

#### 여기서 정한 것

- **고치는 길은 `edit.ts` 하나뿐이다.** 노드에 직접 대입하면 `dirty` 를 잊고,
  잊으면 고친 것이 조용히 사라진다. 지금 쓰는 MCP 에서 21건 나온 그 병이다
- **읽을 때만 이스케이프를 푼다.** 나무에는 원본을 그대로 둔다
- `childrenNamed`(바로 아래)와 `findAll`(자손 전부)을 나눴다.
  표 안의 표, 각주 안의 문단처럼 같은 이름이 겹칠 때 자손까지 긁으면 남의 것을 집는다

### 2단계 — `hwpx` (컨테이너 계층) ✅ 끝

**합격 기준을 넘겼다.**

| | |
|---|---|
| 열고 저장 → 바이트 동일 | **문서 161편 / 부품 2027개 / 251.7MB — 실패 0** |
| 전부 다시 써서 저장 → 다시 읽으면 같다 | **XML 부품 1141개 — 실패 0** |
| 한글이 받아들이나 | **기준 파일 23편을 전부 다시 써서 먹였다 — 실패 0** |
| 시험 | 148개 통과 (1단계 62 → 148) |

#### 어떻게 바이트를 지키나

XML 층과 같은 수를 zip 에 쓴다. **손대지 않은 부품은 원본 압축 바이트를 그대로 쓴다.**
다시 압축하지 않으니 deflate 구현 차이가 끼어들 자리가 없다.
지역 헤더의 플래그·시각·여분 필드까지 원본을 들고 있다가 그대로 쓴다.

```
안 고친 부품  →  원본 압축 바이트 + 원본 헤더     그대로
고친 부품     →  다시 압축                        그 부품만
```

#### 실측으로 정한 것 (추측한 것이 아니다)

| | 문서 113편에서 센 것 |
|---|---|
| `mimetype` | 113/113 이 첫 항목, 113/113 이 STORE |
| 여분 필드 | 1396개 부품 전부 0바이트 |
| 데이터 서술자 | 0건 |
| 지역/중앙 헤더 어긋남 | 0건 |
| BinData 압축 | **jpg 57건·png 41건 전부 STORE / bmp 26건·wmf 1건 전부 DEFLATE** |

BinData 규칙을 처음에 "한글은 BinData 를 압축하지 않는다"고 적었다가 세어 보고 뒤집었다.
진짜 규칙은 **이미 압축된 형식은 그냥 담고, 아닌 것은 압축한다** 이다.

#### 여기서 버그를 하나 잡았다 — 그리고 검사의 구멍을 잡았다

기준 파일을 고쳐 저장했더니 한글이 `ref-table-basic.hwpx` 를 **거부**했다.
원인은 직렬화 한 줄이었다.

```
원본 : <hp:tc name="" header="0" …
우리 : <hp:tc name    header="0" …      ← ="" 를 통째로 빠뜨렸다
```

`name=""`(빈 값)과 `name`(등호 자체가 없음)은 값만 보면 똑같다.
구별하려면 **등호가 있었는지를 기억**해야 하는데 그걸 안 들고 있었다.
`Attr.hasValue` 를 넣어 고쳤다.

더 중요한 것은 **왜 왕복 검사가 이걸 못 잡았나** 다.
검사는 *안 고친* 문서만 봤다. 안 고치면 원본 조각을 그대로 뱉으니
**다시 쓰는 길은 한 번도 지나가지 않았다.** 검사가 사실상 아무것도 안 본 것이다.

그래서 두 층 모두에 갈래를 하나씩 더 냈다:

| 검사 | 하는 일 |
|---|---|
| 왕복훑기 `나)` | 모든 노드를 고친 것으로 표시하고 다시 쓴다 → 바이트 동일 |
| 컨테이너훑기 `나)` | 모든 XML 부품을 다시 써서 저장한다 → 다시 읽으면 같다 |
| 한글수용시험 | 기준 파일을 **전부 다시 써서** 한글에 먹인다 |

새 검사가 헛돌지 않는지 확인했다. 버그를 일부러 되살려 놓으니
**802개 부품 가운데 349개**가 걸렸다. 고치기 전에는 전부 통과라고 했던 것들이다.
#### 덤으로 알게 된 것 — 지금 MCP 가 깨진 XML 을 뱉는다

훑는 범위를 바탕화면·문서 폴더까지 넓혔더니 문서 하나가 파싱에서 걸렸다.
`보고서/표기능점검.hwpx` — **지금 쓰는 MCP 가 만든 파일**이다.

우리 파서를 쓰지 않고 태그만 세어 봐도 짝이 안 맞는다:

```
hp:p       여는 것 60 / 닫는 것 64
hp:run     여는 것 63 / 닫는 것 67
hp:t       여는 것 60 / 닫는 것 64
hp:subList 여는 것 48 / 닫는 것 52
hp:tc      여는 것 51 / 닫는 것 52
```

정규식으로 XML 을 수술하면 이렇게 된다. 이 프로젝트를 새로 시작한 이유가 이것이다.

그래서 훑기가 **우리 버그와 깨진 문서를 갈라 말하게** 했다.
갈라 말하지 않으면 둘 중 하나를 놓친다 — 남의 버그를 우리 것으로 떠안거나,
우리 버그를 남 탓으로 덮거나.

#### 만든 것

| 파일 | 하는 일 |
|---|---|
| `zip.ts` | zip 읽기·쓰기. 원본 압축 바이트와 헤더를 들고 있는다 |
| `container.ts` | 부품 이름, manifest 일치 검사, **못 읽을 파일은 저장을 막는다** |
| `빈문서.ts` | 빈 문서 템플릿. **한글이 저장한 파일 그대로** (`검증/템플릿굽기.mjs` 가 굽는다) |

#### 여기서 정한 것

- **저장 전에 검사하고, 걸리면 안 쓴다.** manifest 와 BinData 가 어긋난 파일은 한글이
  그림을 못 찾거나 통째로 거부한다. 써 놓고 나중에 아는 것보다 안 쓰는 게 낫다
- **빈 문서 템플릿은 손으로 쓰지 않는다.** 한글이 만든 것을 굽는다.
  규격을 어겨도 한글은 알려 주지 않고 그 뒤를 조용히 무시한다
- **검사는 자기가 무엇을 봤는지 숫자로 말한다.** 목록에서 113편이 조용히 걸러졌는데
  훑기가 "실패 0건"이라고 한 적이 있다. 0편을 보고 통과라 하면 검사가 거짓말을 하는 것이다

#### 검증 돌리는 법

```
node 검증/전부.mjs          시험 + 넓은 훑기 (한글 없이 돈다)
node 검증/전부.mjs --한글    한글 수용 시험까지
```

훑을 문서 목록은 **돌릴 때마다 새로 모은다.** 묵은 목록을 쓰면 조용히 0편이 된다.

### 3단계 — `doc` (문서 모델) ✅ 끝

**합격 기준을 넘겼다.**

| | |
|---|---|
| ID 로 가리키고, 넣어도 안 밀린다 | 시험으로 굳힘 |

| 표 검사가 남의 문서를 거짓으로 안 잡나 | 표 1292개 가운데 **99.7%** 에 탈 없음 |

#### 문서가 준 id 를 못 쓴다

`hp:p` 에 id 가 있지만 **34391개 가운데 33539개가 한 문서 안에서 겹친다.**
셀·줄·런에는 아예 없다. 그래서 우리가 매긴다.

나무를 들고 있는 동안 **노드 객체 자체**를 열쇠로 삼는다.
앞에 무엇을 넣든 객체는 그대로다 — 그래서 ID 가 안 밀린다.

ID 는 `p_3f2a` 처럼 **번호처럼 안 보이게** 섞는다.
`p_1` `p_2` 로 매기면 모델이 `p_3` 도 있으리라 여기고 셈을 한다.

#### 문단 여백 — 한글은 `hp:case` 를 읽는다

지금 쓰는 MCP 는 이렇게 적어 놓았다:

> `여백·줄간격은 <hp:switch> 안의 case 와 default 양쪽에 같은 값이 들어 있으므로`
> — `HwpxDocument.ts:13515`

실측은 `default = case × 2` 였고, **한글은 case 를 읽는다.**
양쪽에 같은 값을 넣으면 **여백이 두 배가 된다.**
([`../자료/실측.md`](../자료/실측.md) 1항 — 한글에게 네 번 물어 확인했다)

#### 여기서 잡은 큰 버그 — 글을 바꾸면 표가 사라졌다

처음엔 `글바꾸기` 를 "첫 런만 남기고 나머지를 지운다" 로 짰다.
실측(런 49168개):

| 런 안에 든 것 | 런 수 |
|---|---|
| `hp:t` (글) | 38143 |
| `hp:ctrl` | 1294 |
| **`hp:tbl` (표)** | 1269 |
| **`hp:secPr` (쪽 설정)** | 172 |
| `hp:pic` (그림) | 153 |

**글과 표가 같은 런에 든 것이 1134개**다. 런을 지우면 표가 통째로 사라진다.

**단위 시험은 이걸 다 통과했다.** 한글 수용 시험에서
"표 갈래를 0편 확인" 이라고 나와서야 알았다 — 검사가 무엇을 봤는지 숫자로 말하게
해 둔 것이 여기서 값을 했다.

지금은 **`hp:t` 만 건드린다.** 그리고 그 갈래를 단위 시험으로 내렸다.

#### 검사도 두 번 틀렸다

| 내가 틀린 것 | 어떻게 알았나 |
|---|---|
| "셀 여백을 쓰고 hasMargin=0 이면 조용한 실패" | 실제 문서에서 **5748건**이 걸렸다. 한글은 죽은 값을 그냥 남겨 둔다 |
| "표가 있나" 만 보고 복제를 잡으려 함 | 그 문단에 든 것은 표가 아니라 쪽 설정이었다. **글 아닌 것을 전부** 세게 고쳤다 |

검사가 남의 문서를 거짓으로 잡으면 아무도 안 본다.
그래서 **탈**(격자가 깨졌다)과 **주의**(한글은 눈감아 준다)를 나눴다.

#### 만든 것

| 파일 | 하는 일 |
|---|---|
| `결과.ts` | `결과<T>` — **`void` 를 돌려주는 연산이 없다** |
| `식별자.ts` | 안정 ID. 노드 객체를 열쇠로, 번호는 섞어서 |
| `머리글.ts` | 스타일 확보(복제→패치→지문→재사용), 글꼴 7언어, itemCnt |

| `문서.ts` | 얼굴. ID·연산 기록·검사·저장 |
| (owpml) `clone.ts` | 안전한 복제와 지문. 빈 복제는 소리 내어 막는다 |

### 4단계 — `compose` + `server` 최소 ✅ 끝

문서 한 편이 끝까지 나오는 **첫 한 바퀴**.

#### 한 것 ✅

| | |
|---|---|
| **합격 기준** | **교육부 업무계획 6쪽을 `compose` 한 번으로 재현 — 넘겼다** |

#### 합격 기준을 어떻게 넘겼나

`node 검증/교육부6쪽.mjs` 가 한 바퀴를 다 돈다:
원본에서 6쪽을 **우리 표시법으로 되뽑고** → 되풀어 글자가 같은지 보고 →
블록 11개로 `compose` 를 **한 번** 부르고 → 한글로 열어 PDF 로 굽고 → **자로 댄다.**

| 잰 것 | 원본 | 재현 |
|---|---|---|
| 쪽 크기 | 593 × 840pt | 같음 |
| 글 왼쪽 | 44.6pt | 44.5pt (**0.1pt 차**) |
| 글 너비 | 481.9pt | 480.0pt (**1.9pt 차**) |
| 줄 간격 | 22.0pt | **22.0pt** |
| **글자 수** | **814자** | **814자** |

글자가 한 자도 안 틀린다. 쪽 번호만 다르다 (원본은 6쪽, 우리는 1쪽 문서라 `- 1 -`).

**줄이 3줄 다르게 끊기는 것은 우리 탈이 아니다.**
원본은 어구마다 자간을 손으로 달리 줬다 — 한 문단 안에 `-7 / -6 / -4 / 0` 이 섞여 있고
12pt 런까지 있다. 우리는 고르게 준다. 원한다면 블록마다 `letter_spacing` 으로 맞출 수 있다.

#### 시각 검증이 두 번 값을 했다

둘 다 **XML 이 맞고 검사도 통과했는데** 렌더를 보고서야 알았다.

**하나 — 표 본문이 통째로 남색이 됐다.**
구운 셀 조각이 원본 문서의 `borderFillIDRef="3"` 을 그대로 들고 있었다.
새 문서에서 3번은 **방금 띠 블록이 만든 남색 배경**이었다.

> 구운 조각의 IDREF 는 **딴 문서에서 딴 것을 가리킨다.** 반드시 갈아 끼운다.

**둘 — 상자가 줄마다 네모로 갈라져 표처럼 보였다.**
줄마다 네 면을 다 둘렀기 때문이다. 첫 줄에 위, 끝 줄에 아래, 가운데는 좌우만 걸게 고쳤다.

#### 재는 쪽도 두 번 틀렸다

| 내가 틀린 것 | 어떻게 알았나 |
|---|---|
| 칠한 네모의 윤곽을 선으로 세어 "안 시킨 테두리" 로 읽음 | 띠의 borderFill 을 열어 보니 네 면 다 `NONE` 이었다 |
| 그래서 `stroke` 만 셌더니 **0개** | 한글은 **테두리도 칠해서** 그린다 |

지금은 그리는 방식이 아니라 **모양**으로 가른다 — 한쪽이 3pt 미만이면 선, 아니면 칠한 자리.

#### 만든 것

| 파일 | 하는 일 |
|---|---|

| `조판.ts` | 블록 → 문단·표. 서식은 문서가 쓰던 것에서 갈라 나온다 |

| `검증/조판수용시험.mjs` | 규격·왕복·시각 **세 겹을 한 번에** |

#### MCP 서버 — 도구 10개

| | |
|---|---|
| 문서 (5) | `create_document` `open_document` `save_document` `close_document` `list_documents` |
| 읽기 (4) | `get_outline` `get_content` `find` `get_styles` — 넷 다 `readOnlyHint` |
| 조판 (1) | `compose` |

**저수준 `Server` 를 쓰고 JSON Schema 를 손으로 쓴다.**
SDK 의 `registerTool` 은 Zod 를 JSON Schema 로 바꿔 주지만 **무엇이 나갈지 우리가 모른다** —
선택 인자 하나가 `anyOf` 로 나가도 알 길이 없다. 그래서 손으로 쓰고 **린터가 지킨다.**

| 린터가 막는 것 | |
|---|---|
| 금지 키워드 | `oneOf` `anyOf` `allOf` `$ref` `additionalProperties` 등 15가지 |
| 튜플형 `items` | 단일 스키마만 |
| 숫자 `enum` | 모델이 못 외운다 |
| 설명 없는 속성 | 모델이 무엇을 넣을지 모른다 |
| 입력 중첩 3단계 초과 | 넘으려면 **왜인지 적어야** 한다 (`중첩예외`) |

중첩 한도를 입력 3 / 출력 4 로 나눴다 — **목록-레코드는 본질적으로 4단계**이고
(`$ → matches → matches[] → matches[].id`) 출력은 함수 선언으로 안 바뀐다.
`compose` 만 6단계 예외를 두고 까닭을 적었다 (블록 목록은 본질적으로 배열이다).

#### 순수 Node 로 도는지 **실제로 띄워서** 본다

`검증/서버시험.mjs` 는 안쪽 함수를 안 부른다. 진짜로:
`node bin/hwpx-mcp.mjs` 를 **자식 프로세스로 띄우고** stdio 로 JSON-RPC 를 주고받는다.

Draftsmith 가 `ELECTRON_RUN_AS_NODE=1` + `process.execPath` 로 띄우기 때문이다
(`03-MCP-규격과-범용성.md` 규칙 1-1). 안쪽 시험만 통과하고 진입점이 안 뜨면 앱에서는 아무것도 안 된다.
그리고 stdio 로 말하므로 **표준출력에 아무거나 쓰면 프로토콜이 깨진다** — 그것도 여기서만 잡힌다.

거기서 같이 보는 것: 결과가 세 겹인가 · 읽기 도구에 `readOnlyHint` 가 붙었나 ·
`tools/list` 순서가 늘 같은가 · 못 하는 것을 **`isError` 와 「어떻게」로** 돌려주나.

#### 그림 — BinData 와 manifest 를 한 번에

둘이 어긋나면 한글이 그림을 못 찾거나 파일을 통째로 거부한다.
지금 쓰는 MCP 는 이 둘을 따로 관리해서 실제로 어긋난 적이 있다. 그래서 한 함수에서 같이 한다.

- 크기가 **일곱 군데**에 적힌다 (`orgSz` `curSz` `rotationInfo` `imgRect`(네 점) `imgClip` `imgDim` `sz`).
  한 곳만 고치면 한글이 잘라 그리거나 비율이 뭉개진다.
- **`hashkey` 는 안 적는다.** 한글이 적는 값은 파일 바이트의 md5·sha1·sha256 **어느 것도 아니다**(재 봤다).
  흉내 낼 수 없으니 안 적고, **한글이 받는지 실제로 먹여 확인했다** — 받는다.
- 같은 바이트를 두 번 넣으면 파일을 다시 안 넣는다.

#### 아직 안 한 것

- [ ] 쪽 테두리 · 머리말 · 꼬리말 (6단계 기능 목록에서 채운다)
**합격**: 교육부 업무계획 6쪽을 `compose` 한 번으로 재현하고 렌더로 대조한다.
지금 MCP 로 만든 것과 **같거나 낫다.**

#### 만든 것

`npm test` → `node 검증/전부.mjs` (한글 없이 8갈래)
`npm run test:한글` → 한글 수용 시험까지 15갈래

**저장 길목의 규격 검사** (`문서.저장`)
막는 것은 흠의 있고 없고가 아니라 **늘었나**다. 열 때 흠을 찍어 두고,
우리가 새로 낸 것만 막는다. 남이 만든 문서에도 흠이 있기 때문이다 —
161편을 훑으니 표 기하만 64건이고, 교육부 문서에도
'셀 폭과 열 폭 합이 다르다' 가 있다. 그걸 이유로 **열고 그대로 저장하는 것까지
막으면 쓸 수 없는 도구**가 된다.

고장 내 보니 양쪽 다 잡힌다:
- 검사를 빼면 → 시험 4개가 깨진다
- 원래 있던 흠까지 막게 하면 → 시험 1개가 깨진다

두 번째를 잡으려고 **흠이 있는 문서를 시험 안에서 만들었다.**
기준 파일이 다 멀쩡해서, 안 만들었더니 그 시험이 헛돌았다.

**기능 감사** (`검증/기능감사.mjs`)
가장 나쁜 실패는 터지는 것이 아니라 **조용한 무동작**이다.
지금 쓰는 MCP 에서 실제로 겪었다 — `set_paragraph_style` 에 `margin_left: 20`
을 주면 "Paragraph style applied" 라고 답하는데 **0 이 쓰인다.**

도구 10개를 다 불러 보고 묻는다:
- 고치는 도구가 "됐다" 했으면 **정말 바이트가 달라졌나**, 넣은 글이 문서에 있나
- 읽는 도구가 **문서를 더럽히지 않았나** (읽고 저장했을 때 바이트가 같나)
- 못 하는 것을 **못 한다고 말하고 길까지 알려 주나** (거절 5갈래)
- 감사가 **안 불러 본 도구가 없나** (있으면 감사가 거짓말이다)

고장 내 보니 셋 다 잡힌다: compose 무동작 / close 가 손잡이를 안 지움 /
읽기가 문서를 더럽힘.

### 6단계 — 기능 채우기 ✅ 끝 (한 번 물렀다가 다시 받았다)

**한 번 합격이라 적었다가 물렀다.** 기능표 43/58 은 맞았지만,
그 58가지를 **전부 `create_document` → `compose` 로만 쟀기** 때문이다.
**양식을 열어 고치는 길은 한 번도 재지 않았다** — 그 길이 통째로 없는 줄도 몰랐다.

8단계에서 `edit` 을 내고 **기본 양식 셋을 도구만으로 채우는 것**까지 확인했다.
그래서 다시 받는다. 기능표는 **59가지 가운데 44가지**다.

| 기능 | 쓰임 | |
|---|---|---|

| 탭 | 9% | ✅ |

| 아직 없는 것 | 몇 편에 | 할까 |
|---|---|---|
| 쪽 테두리·배경 | 4편 (2%) | 나중 |

> 만들 일은 없어도 **왕복에서 사라지면 안 된다.**

> **쪽 테두리를 처음엔 99% 로 셌다.** `hp:pageBorderFill` 요소가 구역마다 늘
> 있기 때문이다. 실제로 테두리를 가리키는 것은 474곳 가운데 10곳뿐이었고
> 그마저 한 편이다. **요소가 있는 것과 쓰이는 것은 다르다.**

### 7단계 — 범용성과 배포

- ✅ Claude·Codex·Gemini 에서 실제로 돌려 확인표를 채운다
- ✅ 스키마 린터 (금지 키워드가 있으면 빌드를 깬다)

**합격**: 세 클라이언트에서 같은 문서가 나온다. — **됐다**

#### 만든 것

**세 클라이언트 확인표** (`검증/세클라이언트.mjs`)

| 클라이언트 | 보낸 판 | 서버 판 | 도구 | 문서 만들기 |
|---|---|---|---|---|
| Claude | 2025-06-18 | 2025-06-18 | 10 | ○ |
| Codex | 2025-03-26 | 2025-03-26 | 10 | ○ |
| Gemini | 2024-11-05 | 2024-11-05 | 10 | ○ |

셋은 각자 다르게 두드린다 — 프로토콜 판이 다르고, `initialized` 알림을
안 보내는 쪽이 있고, `tools/list` 를 `params` 없이 보내는 쪽이 있다.
셋 다로 두드려 **같은 도구 열 개**를 보고 **문서를 만들 수 있는지**까지 본다.

> 실제 CLI 를 안 쓴 까닭: 붙이려면 사용자의 `~/.claude.json` ·
> `~/.codex/config.toml` · `~/.gemini/settings.json` 을 고쳐야 한다.
> **남의 설정을 시험이 건드리면 안 된다.** 그래서 같은 모양의 JSON-RPC 를 직접 보낸다.

**꾸러미 시험** (`검증/꾸러미시험.mjs`)

`npm pack` → 빈 폴더에 `npm install` → 순수 Node 로 띄워 말을 건다.
`npx hwpx-mcp` 가 하는 일이 이것이다. 짠 것은 **85KB, 36개 파일**이다.

저장소 안에서는 도는데 짜면 안 도는 일이 흔하다 — `files` 에 안 적어 `dist` 가 안 담기거나,
꾸러미끼리의 `@hwpx/*` 이름이 안 풀리거나, `bin` 경로가 틀리거나.
**저장소 안 시험은 그걸 하나도 못 잡는다.** `files` 에서 `dist` 를 빼 보니 걸렸다.

> **묵은 `dist` 를 보고 있었다.** 진입점은 `dist/` 를 불러 쓰는데
> 세클라이언트 시험이 그걸 안 굽고 돌았다. 도구를 하나 빼는 고장을 냈는데도
> 안 걸려서 알았다. 이제 두 시험 다 `--배포` 를 먼저 굽는다.

### 8단계 — **고치는 도구** ✅ 끝 (새로 세운 단계)

#### 왜 이 단계가 생겼나

7단계까지 다 끝냈다고 적은 날, Draftsmith 세션에 물었다.
"너희가 실제로 쓰는 도구와 차례를 알려 달라."
돌아온 답을 보고 **우리 도구 열 개로는 Draftsmith 를 못 돌린다**는 것을 알았다.

우리 도구 가운데 문서를 **고치는** 것은 `compose` 하나뿐이고,
그건 **뒤에 새로 붙이기만 한다.** 열어 놓은 문서의 문단을 갈거나
표 칸을 채우는 길이 **없다.**

> **"양식 채우기 57판 무탈" 이라고 보고했는데, 그건 문서 층을 직접 부른 것이다.**
> `검증/양식채우기.mjs` 는 `d.글바꾸기(…)` 를 쓴다 — MCP 도구를 안 거친다.
> **모델은 그 길을 쓸 수 없다.**

같은 함정을 오늘 두 번 밟았다. 아침에는 `image` 블록이 조판에 다 있는데
스키마에 자리가 없어 못 썼다. 막이(`블록표면.test.ts`)까지 세웠는데,
**그 막이는 `compose` 블록 필드만 본다.** 도구 표면이 실제 **작업 흐름**을
덮는지는 아무도 안 보고 있었다. 기능표 58가지도 전부
`create_document` → `compose` 로만 재서 이걸 못 잡았다.

#### Draftsmith 가 실제로 쓰는 것

앱은 MCP 를 직접 안 부른다. AI CLI 가 부르고, 무엇을 어떤 차례로 부를지는
**앱이 실어 보내는 작성 지침**이 정한다. 그 지침이 못박아 둔 차례:

1. `open_document` 로 사본을 연다
2. `get_document_structure` — 구역·문단·표를 **센다** (이 숫자를 기억한다)
3. `get_document_text` — 전체를 읽는다
4. `get_tables_summary` → `find_table_by_header` → `get_table_map` 으로 표 위치 확정
5. **채운다**
6. `save_document`
7. **`get_document_structure` 를 다시 불러 처음 수와 견준다.** 크게 줄었으면 되돌린다

지침이 못박은 규칙:
- 문단을 갈 때는 반드시 **서식을 지키며** (`…_preserve_styles`)
- 한 칸씩 여러 번보다 **묶어서** (`batch_fill_table`) — 한 칸씩 넣다 줄이 밀린 적이 있다
- 줄이 모자라면 **줄을 넣는다**, 표를 새로 만들지 않는다
- **새로 만들지 않는다** — 양식이 있으면 열어서 채운다

쓰는 갈래는 셋뿐이다: **표 · 문단 · 그림.**
쪽 머리말·꼬리말도 도형도 안 쓴다 (가정통신문의 '머리글' 은 맨 위에 있는 **보통 표**다).

#### 한 일

- [x] **고치는 도구 `edit`** — 도구를 늘리지 않고 `op` 로 가른다
      (`set_text` · `replace` · `set_style` · `insert_row`)
- [x] 세는 것 — `open_document` 가 구역·문단·표 수를 낸다. 다시 열면 다시 센다
- [x] 대응표 — Draftsmith 에 보냈다
- [x] **기본 양식 셋을 도구만으로 채웠다** (`검증/양식도구.mjs`)

| 양식 | 문단·표 | 달라진 픽셀 |
|---|---|---|
| newsletter.hwpx | 49·2 → 49·2 그대로 | 0.072% |
| plan.hwpx | 84·3 → 84·3 그대로 | 0.039% |
| report.hwpx | 90·3 → 90·3 그대로 | 0.039% |

한 곳만 고쳤을 때의 값이다. 나머지는 안 건드려졌다는 뜻이다.

- [x] **셀에 그림** — `edit` / `op:"insert_image"`
      (교표 자리 셀에 넣어 한글이 그리는 것까지 눈으로 봤다)
- [x] **`get_outline` 이 표 안까지 낸다** — `in_tables: true`
      (newsletter 는 문서 전체가 문단 하나에 든 표 둘이라 뼈대가 1개로 나왔다.
      켜면 셀까지 나오고, 그 ID 로 바로 고칠 수 있다. 빈 칸은 안 낸다)

#### 남은 일

- [ ] 지우기 (`delete_paragraph` · `delete_table`) — Draftsmith 지침에 있긴 하나
      "양식을 채운다" 는 흐름에서는 거의 안 쓴다. 급하지 않다

**합격**: 기본 양식 셋을 **MCP 도구만으로** 열어 채우고 저장했을 때,
안 건드린 곳의 픽셀이 0 이고 문단·표 수가 그대로다. — **됐다**

도구는 **열한 개**가 됐다. 옛 MCP 의 30개(그 가운데 고치는 것 11개)를
`edit` 하나로 받는다 — `op` 로 가른다:
`set_text` · `replace` · `set_style` · `insert_row` · `insert_image`.

#### 가다가 잡은 것

**숫자를 못박은 시험이 깨졌다.** `꾸러미시험`·`세클라이언트` 가
"도구가 10개여야 한다" 고 적혀 있었는데, `edit` 을 더하니 11개가 되어 갈래가 깨졌다.
재는 것은 "몇 개냐" 가 아니라 **"소스가 정의한 것이 다 깔렸냐"** 다.
소스 목록과 견주게 고치고, 대신 **12개를 넘으면 걸리는** 천장을 뒀다 —
적은 것이 이 도구의 성질이기 때문이다.

#### 검증에도 구멍이 있었다

`검증/양식채우기.mjs` 와 `검증/기능표.mjs` 를 **도구 표면으로** 다시 돌려야 한다.
문서 층을 직접 부르는 시험은 문서 층만 지킨다.

### 9단계 — 쓰는 쪽이 적은 대로 도구가 답하게

Draftsmith 가 새 지침 초안을 써 왔다. 그 초안을 읽고
**초안이 적은 대로 도구가 실제로 답하는지** 하나씩 대 봤다.
세 군데가 어긋났는데, **초안이 틀린 게 아니라 도구가 그 일을 못 하고 있었다.**

| 초안이 적은 것 | 그때 도구 | 고친 것 |
|---|---|---|
| `get_content(doc_id)` 로 전체 흐름을 읽는다 | `id` 가 필수라 거절 | `id` 없이 부르면 문서 전체 글 |
| `find(kind:"table")` 로 빈 표를 고른다 | 답에 `id·kind·preview` 뿐 | `rows·cols·empty` 를 더 낸다 |
| `get_content(id:"tbl_…")` 로 셀 id 를 다시 받는다 | `cells` 가 **글자만** 든 배열 | `{id, text, row, col}` 와 `empty` |

세 번째가 특히 그랬다. 초안은 "가운데에 줄을 넣었으면 id 를 다시 받아서 쓴다" 고
옳게 적었는데, **거기서 id 를 받을 길이 도구에 없었다.**
쓰는 쪽 지침을 읽지 않았으면 못 찾았을 구멍이다.

#### 겹친 글자 — 고쳤다가 다른 것을 깨뜨렸다

같이 잡은 것. 칸에 긴 글을 넣으면 글자가 겹쳐 뭉갰다. 원인은 묵은
`hp:linesegarray` 였고, 글을 갈 때마다 지우게 해서 겹침은 없앴다.
**그런데 양식 채우기 57판 가운데 2판이 깨졌다** — 글자 수가 똑같은 글로 채웠는데
정부 문서 23쪽이 26쪽이 됐다.

지운 자리를 한글이 다시 재는데 **다시 잰 값이 원래 값과 다르다.**
그래서 **짜임(글자 수 + 폭 갈래)이 달라졌을 때만** 지우게 했다. 둘 다 됐다.
잰 것은 [`자료/실측.md` 15장](../자료/실측.md)에 적었다.

한 고침이 다른 갈래를 깨뜨렸다는 것은 **갈래를 다 돌려 봐야만** 안다.
낱개 시험 135개는 그때도 다 통과했다.

#### 안내하는 말이 시킬 수 없는 것을 시키고 있었다

Draftsmith 지침 초안을 도구에 대 보다가 잡았다. 없는 id 를 주면 이렇게 말했다.

    → ID매기기() 를 먼저 부르거나, 문서를 다시 열어라.

**`ID매기기()` 는 안쪽 함수다.** MCP 로 부르는 쪽에는 그런 것이 없다.
저장 길목의 「`기록()` 에 무엇을 했는지 남아 있다」 도 같았다.

우리 시험은 다 우리 함수를 알고 부르니 **이 흠을 볼 수가 없다.**
쓰는 쪽 지침을 읽어야만 보인다. 둘 다 부르는 쪽이 실제로 할 수 있는 말로 고쳤다.

#### 옛 MCP 는 셀 안의 표를 못 본다 — 직접 확인했다

Draftsmith 가 대조 결과를 보내 왔다. 전해 들은 것을 그대로 옮기지 않고
**같은 파일을 옛 MCP 에 직접 열어 봤다.**

    open_document        sections: [{ paragraphs: 1, tables: 1, images: 0 }]
    get_tables_summary   표 1개 — "2x3"

가정통신문 회신서(3x7)가 바깥 표(2x3) 칸 안에 있는데 **표가 1개로 보인다.**
그러니 시키는 쪽은 바깥 표를 고를 수밖에 없고, 거기 줄을 넣으면 회신서까지 복제된다.
**틀린 표를 고른 것이 아니라 고를 수가 없는 것이다.**
새 쪽은 `tbl_uylc(2x3)` 와 `tbl_glzp(3x7) in_cell=cell_uylc_1_0` 을 다 낸다.

#### 「도구가 맞게 답하나」 와 「쓸 만한 문서가 나오나」 는 다른 물음이다

Draftsmith 에게 **지침대로 실제 통신문을 한 편 끝까지 만들어 보라** 했다.
도구 여덟 가지가 다 맞는데도 **나온 문서는 못 쓸 것**이었다.

    안녕하십니까?
    ○ 일시 : …          ← 인사말 본문이 통째로 비었다

그 자리가 **빈 문단**이었다. 지침은 「`find(text: …)` 로 잡는다」 로만 적혀 있었고,
**글이 없는 자리는 낱말로 절대 못 찾는다.** 채울 것이 있는 줄도 모르고 지나간다.

도구는 답을 갖고 있었다 — `find(kind:"paragraph")` 는 빈 문단도 낸다.
다만 지침이 **차례가 문서 순서**라는 것을 전제로 쓰므로 시험으로 못 박았다
(`walk` 가 자식 차례대로 내려가는 전위 순회라 문서 순서가 맞다).

그리고 **문단에도 `in_cell` 을 붙였다.** 표에는 이미 붙어 있었다.
빈 문단이 어느 칸 안인지 알아야 곧바로 집는다. 셀 안의 표까지 내려가
**가장 안쪽 칸**을 가리킨다 — 실제 회신서에서 문단 49개 가운데 17개가 회신서 안이다.

#### 합성한 기준파일이 한글을 멈춰 세웠다

회신서 꼴(표 안의 표) 기준파일이 없어 **표를 자기 자신 안에 본떠** 만들었다.
우리 규격 검사도, 저장 길목도 통과했다. **한글은 열다 멎었다** — 10분을 기다려도
안 돌아왔다. 표 id 가 겹친 것을 고쳐도 마찬가지였다.

`검증/한글수용시험.mjs` 는 기준파일 폴더를 통째로 훑는다.
그대로 뒀으면 **그 갈래가 영영 멎었을 것**이다.

합성을 버리고 **실제로 쓰는 빈 서식**(가정통신문 회신서, OOO 자리표만 든 것)을 넣었다.
한글이 기준파일 24개를 다 연다.

**기준파일은 한글이 실제로 여는 것만 넣는다.** 우리 검사를 통과하는 것과
한글이 여는 것은 다르다 — 그게 이 프로젝트가 처음부터 재 온 것이다.

#### 조용히 잘리는 것이 안 되는 것보다 나쁘다

Draftsmith 가 계획서로 옮겨 가자마자 나왔다. `find` 의 기본 한도가 50 이었다.

| 양식 | 문단 | 기본 한도가 주던 것 |
|---|---|---|
| 가정통신문 | 49 | 49 ○ |
| 계획서 | 84 | **50** — 34개 안 보임 |
| 보고서 | 90 | **50** — 40개 안 보임 |

무엇이 잘렸는지가 문제였다. 계획서 51번째 뒤에 이런 것이 있었다.

    p_v7l5                   4. 예산사용계획
    p_2idv  cell_40cp_0_0    예산사용
    …                        (예산 표의 빈 칸 24개)

지침대로 「`kind:"paragraph"` 로 훑어 빈 자리를 채운다」 를 하면
**앞 세 절만 채우고 예산 표를 빈 채로 두고 끝낸다.** 예산 없는 계획서는 결재가 안 난다.
그리고 **부르는 쪽은 자기가 뭘 안 봤는지 모른다.**

도구는 거짓말은 안 했다 — 사람 말로 "(앞 50개만)" 이라 했고 `count` 도 옳았다.
그것으로는 모자랐다. `count` 와 `matches.length` 를 견주라고 맡겨 두면 아무도 안 견준다.

셋 다 고쳤다.

1. **훑기(`kind` 만)의 기본을 500 으로.** 훑기는 본디 전수다.
   찾기(`text` 있음)는 50 그대로 — 그건 겨눈 것이다.
2. **답에 `truncated` 를 담는다.** `find` 와 `get_outline` 둘 다.
3. **잘렸으면 무엇을 하라고 말한다** — "limit 을 키워 다시 불러라".
   도구 설명에도 넣었다. 지침을 안 읽은 모델도 걸리는 자리다.

이 흠은 우리가 **더 좋은 길을 안내한 그 자리**에 있었다.
「빈 자리를 찾을 때는 훑어라」 를 도구 설명에 넣었는데, **훑기가 한도에 제일 잘 걸린다.**

#### 검증이 배포용을 안 구웠다

`전부.mjs` 는 `.빌드전체`(시험용)만 구웠다. **`dist`(배포용)는 안 구웠다.**
그러니 19갈래가 다 통과해도 dist 는 묵을 수 있었다.
`꾸러미시험` 은 dist 를 짜서 **파일이 있나만** 보지 언제 구운 것인지는 안 본다.

실제로 도구 셋을 고치고 검증을 다 돌렸는데, dist 를 물고 있던 쪽은 옛 동작을 보고 있었다.
**「내가 보는 것」과 「남이 물고 쓰는 것」이 달랐다.**
`['배포용 굽기 (dist)', 빌드.mjs --배포]` 갈래를 넣었다.

#### 한 칸에 문단이 여럿이면 — 조용한 반쪽 쓰기

`문단찾기` 는 칸을 주면 **첫 문단만** 집는다. 그래서 이랬다.

    set_text(cell_…, '갈아 넣은 글')
    → 칸 글: "갈아 넣은 글둘째 줄 글"     ← 둘째 줄 옛 글이 남았다
    → 사람 말: "1곳이 바뀌었다"           ← 거짓말은 아니다. 그래서 더 나쁘다

읽는 쪽도 같았다. `get_content(cell_…)` 이 다 이어 붙여
`"첫 줄 글둘째 줄 글"` 을 줬다. **두 줄인 줄도 모르고, 그대로 다시 넣으면 한 줄이 된다.**

실제 계획서 양식에 그런 칸이 4개 있었다. 셋 다 고쳤다.

1. `칸글바꾸기` — 줄바꿈으로 문단을 나눠 넣고 **남는 문단은 비운다.**
   줄이 문단보다 많으면 **거절한다** — 말없이 합치면 줄이 사라진 줄도 모른다.
2. `get_content(cell_…)` 이 `text` 를 줄바꿈으로 갈라 주고 `paragraphs` 로 **문단 ID 까지** 준다.
3. 표를 통째로 볼 때의 `cells[].text` 도 갈라 준다.

#### 고장을 심어 보고서야 시험이 헛돈 것을 알았다

넷을 심었는데 **셋이 안 잡혔다.**

- 둘은 **고장 낸 파일과 시험 돌린 꾸러미가 달랐다** — `packages/doc` 을 고쳐 놓고
  `packages/doc` 시험만 돌렸는데, 그 동작을 보는 시험은 `packages/server` 에 있었다.
  **문서층 것은 문서층 시험이 지켜야 한다.** 여섯 개를 새로 적었다.
- 하나는 **아무도 안 보던 자리**였다. `text` 에 줄바꿈이 들어가는지 재는 시험이 없었다.

그리고 시험 자체가 헛돌 뻔했다. 문단 둘인 칸을 `ref-table-basic` 에서 찾았는데
**그 파일 칸에는 문단이 하나뿐**이라 `if (문단수 < 2) return;` 으로 조용히 건너뛰었다.
건너뛰기를 없애고 **문단 둘인 칸을 실제로 찾아 못 박았다.**

#### 그래서 헛도는 시험을 찾는 갈래를 만들었다

한 번 훑고 말면 다시 생긴다. `검증/헛도는시험.mjs` 가 세 가지를 잡는다.

| 잡는 것 | 왜 |
|---|---|
| 앞에 `expect` 가 없는 `if (…) return;` | 그 갈래에서는 아무것도 안 본다 |
| **이 기계에 있는** 저장소 밖 절대 경로 | 여기 있어서 통과할 뿐이다 |
| `expect` 가 하나도 없는 `it` | 돌기만 한다 |

`if (r.ok) return;` 처럼 **앞 줄에서 이미 못 박은 것**은 타입 좁히기라 넘어간다.
「일부러 없는 경로」(`C:\없는곳\없다.png`)도 넘어간다 — 없어야 뜻이 있는 것이다.
그래서 **이 기계에 실제로 있는지**로 갈랐다.

돌려 보니 둘이 나왔다. 둘 다 `gemini-studio` 의 양식 파일을 가리키고 있었고,
그 파일이 없는 기계에서는 **아무것도 안 재고 통과**했다.
저장소 안 기준파일로 옮겼다.

이 갈래는 **고장내보기보다 먼저** 돈다. 헛도는 시험은 고장을 내도 안 잡히기 때문이다.

## 지금 것은 언제까지 쓰나

새 것이 **6단계를 통과할 때까지** 지금 MCP(`wonmukoh/hwpx-mcp`)를 계속 쓴다.
그때 나란히 두고 같은 문서를 만들어 대 본 뒤 **Draftsmith 를 갈아탄다.**

새 프로젝트가 지금 것을 대체하기 전에는 **지금 것을 건드리지 않는다.**

### 왜 4단계가 아니라 6단계인가

4단계 합격 기준은 "문서 한 편이 끝까지 나온다" 다 — **한 바퀴가 도는지**를 본다.
그건 갈아탈 근거로 모자란다. 4단계를 넘겨도 기능 목록의 절반은 비어 있고,
Draftsmith 가 실제로 쓰는 것 가운데 아직 없는 것이 남는다
(그림 넣기, 쪽 설정, 머리말·꼬리말, 각주, 양식 채우기…).

**6단계는 기능 목록의 '목표' 칸이 다 채워지는 때**다.
그때라야 "지금 것과 같거나 낫다" 를 기능별로 대 볼 수 있다.
반쯤 채운 것으로 갈아타면 Draftsmith 가 두 번 일한다.

| 언제 | 무엇을 하나 |
|---|---|
| 4단계 통과 | 첫 한 바퀴가 돈다. **알리기만 한다** — 갈아타지 않는다 |
| 5단계 통과 | 검증이 `npm test` 하나로 다 돈다 |
| **6단계 통과** | **Draftsmith 에 적용한다.** 이때 그쪽 세션에 신호를 보낸다 |
| 7단계 | 세 클라이언트(Claude·Codex·Gemini) 확인과 배포 |

갈아탈 때 지킬 것은 [`03-MCP-규격과-범용성.md`](03-MCP-규격과-범용성.md) 규칙 1-1 에 있다
(진입점이 순수 Node, `NODE_EXTRA_CA_CERTS` 보존, 그림은 절대 경로).

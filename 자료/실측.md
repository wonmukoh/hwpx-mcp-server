# 실측

**여기 적힌 것은 전부 세어 보거나 한글에게 물어본 것이다.** 추측은 여기 못 들어온다.

각 항목에 **어떻게 알았는지**와 **다시 재는 법**을 적는다.
말이 바뀌면 재는 법도 같이 바꾼다.

지금까지 **내 추측이 세 번 뒤집혔다.** 그래서 이 문서가 있다.

## 1. 문단 여백 — `hp:case` 가 진짜다

`paraPr` 의 여백·줄간격은 `hp:switch` 안에 **두 번** 들어 있다.

```xml
<hp:switch>
  <hp:case hp:required-namespace="http://www.hancom.co.kr/hwpml/2016/HwpUnitChar">
    <hh:margin><hc:left value="2835" unit="HWPUNIT"/>…</hh:margin>
    <hh:lineSpacing type="PERCENT" value="160" unit="HWPUNIT"/>
  </hp:case>
  <hp:default>
    <hh:margin><hc:left value="5670" unit="HWPUNIT"/>…</hh:margin>
    <hh:lineSpacing type="PERCENT" value="160" unit="HWPUNIT"/>
  </hp:default>
</hp:switch>
```

### 규칙

| | |
|---|---|
| 한글이 읽는 쪽 | **`hp:case`** |
| 한글이 쓰는 쪽 | `hp:default` = `hp:case` × 2 |
| 한글 API(HWPUNIT)가 말하는 값 | `hp:default` 값 |
| **길이 V(HWPUNIT)를 주려면** | `hp:default` = V, **`hp:case` = V / 2** |
| 백분율(`PERCENT` 줄간격) | 길이가 아니다 — **두 갈래가 같다** |

### 어떻게 알았나

세어서는 알 수 없었다. 161편에서 `default / case` 비율을 세니
`2` 가 8145개, `1` 이 8352개(전부 `PERCENT` 줄간격), 둘 다 0 이 33555개였다.
비율은 알았지만 **어느 쪽이 진짜인지**는 알 수 없었다.

그래서 한글에게 물었다 — 일부러 **짝이 안 맞는 값**을 주고 무엇을 뱉는지 봤다.

| 넣은 것 | 한글 API 가 말한 여백 | 한글이 다시 쓴 것 |
|---|---|---|
| case=9000 default=1000 | 18000 | case=9000 default=18000 |
| case=1000 default=9000 | 2000 | case=1000 default=2000 |
| case=2835 default=2835 | **5670** | case=2835 default=5670 |
| case=2835 default=5670 | 5670 | case=2835 default=5670 |

네 번 다 **case 를 읽고 default 를 버렸다.**

### 왜 중요한가

지금 쓰는 MCP 는 이렇게 적어 놓았다:

> `여백·줄간격은 <hp:switch> 안의 case 와 default 양쪽에 같은 값이 들어 있으므로`
> — `HwpxDocument.ts:13515`

양쪽에 같은 값을 넣으면 **여백이 두 배가 된다.** 위 표 셋째 줄이 그것이다.

### 다시 재는 법

```
node 검증/문단여백단위.mjs
```

규칙이 깨지면 0이 아닌 값으로 끝난다.

## 8. 셀 여백은 `hasMargin` 을 켜야 산다

`hasMargin=0` 인 셀 18055개 가운데 **5748개**가 표 여백과 다른 `cellMargin` 을 갖고 있었다.
써 놓고 안 쓰이는 것인가? 세어서는 알 수 없어 한글에게 물었다.

### 어떻게 물었나

한글은 저장할 때 줄 조각(`hp:lineseg`)을 다시 계산한다.
`horzsize` 가 그 셀 안에서 글이 놓일 너비다:

```
horzsize = 셀 너비 − 왼쪽 여백 − 오른쪽 여백
```

셀 너비 13984, 표 안여백 510/510, 셀 여백 2000/2000 을 주고 한글에게 저장시켰다.

| `hasMargin` | 한글이 쓴 `horzsize` | 셀 여백이면 | 표 여백이면 | 판정 |
|---|---|---|---|---|
| `0` | **12964** | 9984 | 12964 | **표 여백을 썼다** |
| `1` | **9984** | 9984 | 12964 | **셀 여백을 썼다** |

### 규칙

- `hasMargin=0` → `cellMargin` 은 **죽은 값**이다. 표의 `inMargin` 이 쓰인다.
- 셀 여백을 주려면 **`hasMargin="1"` 을 같이 켠다.**
- 다만 한글이 `hasMargin=0` 인 셀에도 `cellMargin` 을 남겨 두므로,
  **그것만 보고 "문서가 잘못됐다" 고 하면 안 된다** (5748건이 그렇다).

### 다시 재는 법

```
node 검증/셀여백단위.mjs
```

## 10. 재현이 얼마나 충실한가 — 재 보고 나서 안 것

2026-08-26. 교육부 문서 4편(65쪽)과 기준 파일 12개로 두 갈래를 갈랐다.
갈래를 나눈 까닭은, 둘의 결과가 아주 다르기 때문이다.

### 갈래 가) 양식을 받아 채우기 — 픽셀까지 지킨다

원본을 한글로 PDF 로 굽고, 우리가 고친 것도 굽고, **픽셀로 견준다**
(`검증/양식채우기.mjs`, `검증/픽셀대조.py`).

| 무엇을 했나 | 기대 | 잰 것 |
|---|---|---|
| 열고 그대로 저장 | 픽셀 완전 동일 | 양식 16개 전부 **다른 픽셀 0** (29쪽짜리 포함) |
| ID 매기고 저장 | 픽셀 완전 동일 | 양식 16개 전부 **다른 픽셀 0** |
| 문단 3개 글 바꾸기 | 쪽 수 그대로, 바꾼 곳만 | 그대로 |
| 표 전부 채우기 (65개 표 427칸) | 쪽 수·표 기하 그대로 | 그대로 |
| 문단 하나에 글자 서식 | 그 쪽만 달라짐 | 그대로 |

### 갈래 나) 처음부터 조판하기 — 글은 맞고, 서식은 빠진다

원본 쪽의 문단을 우리 표시법으로 되뽑아 `compose` 한 번으로 만든 뒤
원본 쪽과 견준다 (`검증/여러쪽재현.mjs`, `검증/디자인닮음.py`).

디자인 닮음(18쪽 평균):

| 갈래 | 닮음 | 무슨 뜻인가 |
|---|---|---|
| 색 | 98% | 강조색이 산다 |
| 가로 자리 | 88% | 가운데맞춤·들여쓰기·열 자리가 대체로 맞다 |
| 굵기 | 87% | `**굵게**` 가 산다 (오히려 더 굵게 나온다) |
| **선** | **42%** | 표·상자 테두리 굵기가 안 넘어간다 |
| **글자 크기** | **41%** | 크기 갈래 94 → 56. **큰 제목이 안 커진다** |
| 모두 | 71% | |

### 왜 이렇게 갈리나

`compose` 의 `table` 블록은 `headers` + `rows` 만 받는다.
칸마다의 **열 폭·정렬·글자 크기·굵기·테두리 굵기**를 못 받는다.
그래서 표가 많은 정부 문서를 되뽑으면 표가 밋밋한 격자가 된다.

문서 층(`packages/doc`)에는 그 손잡이가 다 있다
(`열폭주기` `세로정렬주기` `안여백주기` `테두리주기`).
**없는 것은 능력이 아니라 조판 층의 입구다.** 6단계에서 채운다.

### 재는 자를 세 번 고쳤다

1. **쪽가르기가 틀렸다.** PDF 글자를 맞춰 "이 문단은 3쪽" 을 되짚는 어림인데,
   빗나가면 남의 문단이 섞인다. 원본 651자 / 재현 1018자 인 쪽을 두고
   "세로로 넘쳐 2쪽이 났다" 고 보고했다. **넘친 게 아니라 잘못 갈랐다.**
   → 글자 수가 5% 넘게 벌어지면 **탈로 세지 않고 '못 갈랐다'** 로 뺀다.
   51쪽 중 32쪽이 여기 걸린다. 그 32쪽은 **잰 적이 없는 것이지 통과한 것이 아니다.**
2. **줄 간격을 중간값으로 쟀다.** 한 쪽에는 갈래가 다른 틈이 섞여 있다
   (줄 사이 16pt, 문단 사이 24pt, 표 줄…). 어느 갈래가 많으냐에 따라
   중간값이 무리를 건너뛴다. → **가장 흔한 틈**, 그것도 5pt 넘는 것만 센다.
3. **픽셀로 디자인을 재려 했다.** 글이 706/708 자로 거의 같은 쪽인데
   닮음이 0.0 이 나왔다 — 세로로 한 줄 밀리면 글자마다 어긋난다.
   그건 **정렬을 잰 것이지 디자인을 잰 것이 아니다.**
   → 글자 크기·굵기·색·가로 자리·선을 **따로** 센다 (`검증/디자인닮음.py`).
   자가 살아 있나: 원본 ↔ 원본 = 1.0.

### 첫 줄만 나가고 둘째 줄이 안 들어가던 것

`○ (참여 대상) …` 같은 개조식 줄은 **왼쪽 여백(`hc:left`)과
내어쓰기(`hc:intent`)** 로 둘째 줄을 글머리 아래로 넣는다.
조판이 이 둘을 안 받아 둘째 줄이 왼쪽 끝까지 나갔고, 줄이 늘어 쪽이 넘쳤다.
`본문블록`·`소제목블록` 에 `indent_left`·`hanging` 을 넣어 고쳤다.

## 11. 쪽은 `hp:lineseg` 의 `vertpos` 로 가른다 — 다만 혼자서는 모자란다

HWPX 에는 "이 문단은 몇 쪽" 이라는 값이 **없다.** 한글이 그릴 때 정해진다.
두 가지 방법을 다 써 봤고, **둘 다 혼자서는 부족했다.**

### 가) PDF 글자 맞추기

PDF 로 굽고 글자를 맞춰 되짚는다. **문단을 잘못 흩는다** —
남의 문단이 섞여 51쪽 가운데 20쪽을 못 쟀다.

### 나) `vertpos` 되돌림

`hp:p` → `hp:linesegarray` → `hp:lineseg@vertpos` 는 **쪽 안에서의 세로 자리**다.
쪽이 넘어가면 0 가까이로 되돌아간다. 되돌아간 횟수 + 1 = 쪽 수.

| 문서 | `vertpos` | 한글 |
|---|---|---|
| 보도자료 | **3** | **3** |
| 대학혁신 기본계획 | 22 | 23 |
| 업무계획 | 9 | 10 |
| 전문대학 기본계획 | 27 | 29 |

잘 묶지만 **쪽 수가 모자란다.** 표가 쪽을 넘어 이어질 때 그 나눔이 안 보인다 —
표 하나는 문단 하나 안에 통째로 들어 있고, 그 문단의 `linesegarray` 는
한 번만 적히기 때문이다. 그래서 쪽 번호가 PDF 와 어긋난다.

### 그래서 섞는다

**묶기는 `vertpos` 로, 번호는 PDF 로.** 각 묶음이 몇 쪽인지는
그 안 문단들의 PDF 짐작을 다수결로 정한다. 묶음이 통째로 한 쪽에 앉으므로
남의 문단이 안 섞인다.

잰 쪽이 **31 → 35** 로 늘었고, 탈 없는 쪽이 3 → 5,
디자인 닮음이 74.2 → 75.0% 가 됐다.

### 덧붙여

우리가 만든 문서에는 `linesegarray` 가 **아예 없다.**
한글로 열었다 저장해도 안 생긴다 — 머리 없이 COM 으로 여닫으면
한글이 줄 기하를 안 적는다. 원본의 것은 사람이 편집하던 때 적힌 것이 남아 있는 것이다.
그래서 이 방법은 **남이 만든 문서에만** 쓸 수 있다.

## 12. 본문 높이는 위·아래 여백만으로 안 정해진다

세로로 넘치는 쪽을 쫓다가 알았다. 문단 여백도, 줄 간격도, 글자 크기도
원본과 **한 자도 안 틀렸는데** 재현이 넘쳤다.

### 잰 것

| | 원본(교육부 기본계획) | 빈 문서 틀 |
|---|---|---|
| 용지 높이 | 84188 | 84186 |
| 위 / 아래 | 4251 / 4251 | 4251 / 4251 |
| **머리말 / 꼬리말** | **2834 / 2834** | **4252 / 4252** |

본문 높이 = `쪽높이 − 위 − 아래 − 머리말 − 꼬리말`

    원본  84188 − 4251 − 4251 − 2834 − 2834 = 70018
    재현  84186 − 4251 − 4251 − 4252 − 4252 = 67180   ← 2838 (28.4pt) 좁다

머리말·꼬리말은 **글을 안 써도 자리를 차지한다.** 위·아래 여백만 맞추면
쪽에 들어가는 줄 수가 달라진다. 28pt 면 15pt 글자 기준 한 줄이다.

### 그래서

- 쪽 여백을 옮길 때 `header` `footer` 도 **같이** 옮긴다.
  `compose` 에 `margin_header` `margin_footer` 를 냈다.
- 정부 문서는 대개 2834 HWPUNIT(=10mm)을 쓴다. 빈 문서 틀은 4252(=15mm)다.

### 효과

여러 쪽 재현에서 **세로로 넘친 쪽이 17 → 9 로 줄었다.**

### 곁들여 — 이걸 찾는 데 얕은 조회로 세 번 헤맸다

`hh:lineSpacing` 도 `hc:left` 도 `hp:switch` **안에** 있다.
`firstChildNamed(paraPr, 'hh:lineSpacing')` 는 늘 `null` 을 준다.
"883개 문단 전부 줄 간격이 없다" 는 헛것을 그렇게 봤다.
속성도 `getAttr` 로 읽어야 한다 — 노드의 `attrs` 를 직접 뒤지면 `undefined` 가 나온다.
**깊이 찾을 것은 `findAll`, 속성은 `getAttr`.**

## 13. 빈 문단도 줄 높이를 차지한다

여러 쪽 재현에서 쪽마다 세로가 10% 안팎 더 먹었다. 쫓다가 알아낸 것.

### 먼저 같다고 확인한 것

교육부 기본계획 5쪽의 두 문단을 원본과 재현에서 **XML 한 줄까지** 대조했다.
다른 것은 `id` 번호뿐이었다 — `hh:paraPr` 전문, `hh:charPr` 전문(7개 언어 글꼴까지),
여백, 줄 간격, 크기, 굵기, 글꼴, 스타일 바탕, 구역 격자, 쪽 여백 전부 같았다.

### 그런데 렌더가 달랐다

    ◦ (사업 기간)   원본 33.9pt   재현 42.8pt
    ◦ (지원 내용)   원본 27.7pt   재현 36.7pt

### 줄 높이 규칙부터 쟀다

`hp:lineseg` 를 문서 161편에서 모아 보니 규칙이 나온다:

    spacing = 글자크기 × (줄간격% − 100) / 100
    줄 높이 = vertsize + spacing = 글자크기 × 줄간격% / 100

| 크기 | 줄간격% | spacing | 확인 |
|---|---|---|---|
| 1500 | 160 | 900 | 1500×0.60 ✓ |
| 1500 | 180 | 1200 | 1500×0.80 ✓ |
| 1200 | 155 | 660 | 1200×0.55 ✓ |

15pt 180% 면 27pt 다. **우리 조판도 26.94pt 로 정확했다** —
같은 줄을 여덟 개 쌓아 PDF 로 재서 확인했다. 조판은 안 틀렸다.

### 범인은 빈 문단이었다

    26.94(글줄) + 16(우리 빈 문단) = 42.9   ← 잰 값과 딱 맞는다
    26.94(글줄) +  7(원본 빈 문단) = 33.9

빈 문단은 **글이 없어도 줄 높이를 차지한다.** 재현하는 쪽에서
빈 문단에 서식을 안 실어 줬더니, 조판이 기본값(10pt·160% = 16pt)을 썼다.
원본의 빈 문단은 7pt 짜리다. **빈 줄마다 9pt 씩 더 먹었다.**

### 그래서

- 문단을 옮길 때 **빈 문단에도 크기·줄 간격을 같이 옮긴다.**
- 세로로 넘친 쪽이 **9 → 6 으로 줄었다** (디자인 닮음 73.1% → 74.2%).

### 아직 남은 6쪽

같은 방식으로 더 쫓아야 한다. `hp:linesegarray` 는 범인이 아니다 —
우리 문서에는 없고 원본에는 있지만, **한글로 열었다 저장해도 한글이 안 쓴다.**
머리 없이 COM 으로 여닫으면 줄 기하를 안 적는다. 원본의 것은 사람이 편집하던
때 적힌 것이 남아 있는 것이다.

## 14. 구역을 더하려면 **네 곳**을 고쳐야 한다 — `secCnt` 가 마지막 하나

실측: 문서 161편 가운데 **10편(6%)이 구역을 나눈다.**

구역 하나를 더하는 것은 부품 하나를 쓰는 일로 안 끝난다. **넷을 다 해야 한다:**

| | 무엇 | 안 하면 |
|---|---|---|
| 1 | `Contents/sectionN.xml` 부품 (차례도 section0 바로 뒤로) | 파일이 없다 |
| 2 | manifest 의 `<opf:item>` | 한글이 그 구역을 못 찾는다 |
| 3 | manifest `<opf:spine>` 안의 `<opf:itemref>` | 순서를 모른다 |
| 4 | **`header.xml` 의 `<hh:head secCnt>`** | **통째로 버린다** |

### 넷째를 찾는 데 한나절이 걸렸다

1~3 을 다 맞췄는데도 한글이 둘째 구역을 버렸다. 글까지 사라졌다.
기준 파일(`ref-section-break.hwpx`)과 하나씩 대 봐도 전부 같았다 —
`<opf:item>` · `<opf:itemref>` · zip 부품 차례 · `META-INF/*` · `version.xml`,
`settings.xml` 은 커서 자리만 달랐다.

**부품을 바꿔 끼워** 보고서야 나왔다:

| 섞은 것 | 결과 |
|---|---|
| 기준 파일 + **우리 section1** | 구역 2개 ○ ← 우리 구역 XML 은 멀쩡했다 |
| 우리 파일 + 기준 section1 | 구역 1개 ✗ ← 범인은 딴 데 있다 |
| 기준 파일 + 우리 `content.hpf` | 2개 ○ |
| 기준 파일 + 우리 **`header.xml`** | **1개 ✗** ← **범인** |
| 기준 파일 + 우리 `section0.xml` | 2개 ○ |
| 기준 파일 + 우리 `settings.xml` | 2개 ○ |

`header.xml` 의 뿌리를 보니 한 글자였다:

    기준  <hh:head version="1.5" secCnt="2">
    우리  <hh:head version="1.5" secCnt="1">

**한글은 이 숫자를 믿고 그만큼만 읽는다.** 부품이 있어도, manifest 에 적혀 있어도,
`secCnt` 가 1 이면 둘째 구역은 없는 것이 된다.

### 가다가 잡은 것

처음엔 정규식으로 마지막 `<opf:item id="sectionN">` 을 찾아 그 뒤에 끼웠다.
그런데 **항목이 `</opf:manifest>` 밖으로 나갔다.** 같은 정규식을 따로 돌리면
맞는데 함수 안에서는 안 맞았다 — 까닭은 못 밝혔다.
자리 계산을 없애고 `</opf:manifest>` 앞에 붙이는 것으로 바꿨다.
**목록 안에서의 차례는 규격상 뜻이 없다.** 뜻이 있는 것은 spine 의 차례다.

### 시험이 헛돌던 것도 잡았다

"새 구역에 남의 글이 안 딸려 온다" 를 **빈 문서**로 시험했다.
지울 글이 없으니 무엇을 해도 통과했다 — 글을 안 비우게 고장 냈는데 다 통과했다.
**글이 든 문서**로 바꾸고서야 잡혔다.


## 15. `hp:linesegarray` — 지워도 탈, 안 지워도 탈

`hp:linesegarray` 는 한글이 그릴 때 **재어서 적어 둔 값**이다.
줄마다 몇 째 글자에서 넘어가는지(`textpos`), 어느 높이에 놓이는지(`vertpos`)가 적힌다.

### 안 지우면 — 글자가 겹친다

셀에 10자짜리 글이 있었고 줄 정보에도 "8자까지" 라고 적혀 있었다.
거기에 59자를 밀어 넣었더니 한글이 **적힌 말을 믿고** 한 줄에 다 그렸다.
PDF 로 구워 보니 글자가 서로 포개졌다.

### 지우면 — 쪽이 늘어난다

그래서 글을 갈 때마다 지우게 했다. 겹침은 없어졌는데 **다른 것이 깨졌다.**

정부 문서(23쪽, 표 65개)의 427칸을 **글자 수가 똑같은 글**로 채웠다.
줄이 밀릴 까닭이 없는데 **23쪽이 26쪽이 됐다.**
29쪽짜리는 34쪽이 됐다. 어긋난 쪽이 22곳, 가장 심한 데는 34%가 달랐다.

지운 자리를 한글이 다시 재는데, **다시 잰 값이 원래 적혀 있던 값과 다르다.**
원래 값은 그 문서를 만든 한글이 그때의 글꼴로 잰 것이고,
다시 재는 값은 지금 이 컴퓨터의 글꼴로 잰 것이다. 둘이 늘 같지는 않다.

### 재 보고 정한 것 — 짜임이 달라졌을 때만 지운다

줄이 어디서 넘어가는지는 **글자마다의 폭 갈래**로 갈린다.

| 갈래 | 무엇 | 왜 |
| --- | --- | --- |
| `W` | 한글·한자·전각 | 두 칸 폭. 글자 아무 데서나 줄이 넘어간다 |
| `S` | 빈칸 | 줄이 여기서 넘어간다 |
| `N` | 라틴·숫자·반각 | 낱말 단위로 넘어간다 |

옛 글과 새 글의 **글자 수가 같고 자리마다 폭 갈래도 같으면**,
줄은 똑같은 자리에서 넘어간다. 그러면 원래 줄 정보가 여전히 맞으니 **그대로 둔다.**
하나라도 다르면 지운다.

재 보니 둘 다 됐다.

| | 겹친 글자 자리 | 양식 채우기 |
| --- | --- | --- |
| 늘 두기 (처음) | 44곳 | 57판 무탈 |
| 늘 지우기 | 0곳(원본이 가진 17곳만) | **57판 중 2판 탈** |
| 짜임이 다를 때만 지우기 | 0곳(원본이 가진 17곳만) | 57판 무탈 |

겹침을 셀 때는 **손 안 댄 원본도 같이 재야 한다.**
원본에도 겹친 자리가 17곳 있었다 — 위첨자와 자간 좁힌 자리다.
그걸 빼지 않으면 "17곳 겹쳤다" 를 고침 탓으로 잘못 읽는다.

## 16. 한글이 「파일을 못 연다」 할 때 — **스크립트 인코딩부터 보라**

npm 에 올린 것을 깔아 만든 문서를 한글로 열어 보니 `OPENFAIL` 이 났다.
같은 파일을 ASCII 이름 폴더로 옮기니 열렸다. 「한글 경로를 못 읽는다」 로 보였다.

**아니었다.** 네 경로를 한꺼번에 재 보니 다 열린다.

    OK  ...
pxcheck\out.hwpx
    OK  ...
px-1787890262\out.hwpx
    OK  ...\한글폴더\문서.hwpx
    OK  ...
px시험-1787890262\낸것.hwpx     ← 아까 실패했던 바로 그 파일

차이는 **`.ps1` 파일의 인코딩**이었다.

| 어떻게 썼나 | 결과 |
|---|---|
| bash heredoc (BOM 없는 UTF-8) | 한글 경로가 깨져 **OPENFAIL** |
| `utf-8-sig` (BOM 붙임) | 다 열린다 |

Windows PowerShell 5.1 은 BOM 이 없으면 **시스템 ANSI 코드페이지로 읽는다.**
스크립트 안의 한글 경로가 mojibake 가 되고, 한글은 없는 파일을 열려다 실패한다.

**한글이 못 연다고 할 때 파일부터 의심하면 헛다리를 짚는다.**
시키는 글이 제대로 전달됐는지를 먼저 본다. 한글 경로를 쓰는 `.ps1` 은 **BOM 을 붙여 쓴다.**

## 17. XML 이 **어떤 방법으로도 못 쓰는** 글자가 있다

XML 1.0 은 C0 제어문자 가운데 **TAB(U+0009) · LF(U+000A) · CR(U+000D)** 만 허락한다.
나머지(`U+0000`~`U+001F`)는 **이스케이프로도 못 넘긴다** — `&#0;` 같은 숫자 참조도 안 된다.
`U+FFFE` · `U+FFFF` 도 같다.

이건 「거의 안 쓰니 빼자」 가 아니라 **규격이 표현 자체를 금지한 것**이다.

### 재 본 것

`U+0000` 과 `U+0008` 이 든 글을 넣어 봤다.

    글 넣기      ○ 받아 준다
    저장         ○ 12,002바이트
    XML 안에     U+0000 · U+0008 이 **그대로** 들었다
    한글이 여나   ✗ **OPENFAIL**

**저장이 됐다고 쓸 수 있는 게 아니다.** 파일은 만들어졌는데 한글이 통째로 거절한다.

### 어떻게 막나

**말없이 빼지 않는다.** 빼면 글이 조용히 달라지고, 부르는 쪽은 제가 준 글이
들어간 줄 안다. **몇 번째 글자인지 짚어 주고 멈춘다.**

두 겹으로 건다 —

| 어디 | 왜 |
|---|---|
| `문단.글바꾸기` | 쓰는 길목. 어느 고침이 나빴는지 바로 안다 |
| 저장 길목(`검사`) | 조판·복제 같은 딴 길로 새어 들어와도 잡는다 |

`escapeXml` 은 다섯 기호(`& < > " '`)만 다룬다. 제어문자는 **이스케이프의 일이 아니다** —
바꿔 넣을 것이 없으니 애초에 받으면 안 되는 것이다.

### 한 길만 막으면 딴 길로 샌다

처음엔 `글바꾸기` 한 곳만 막았다. **`replace` 로는 그냥 들어갔다** — 딴 길이었다.
저장 길목이 잡아 주긴 했는데, 그때는 「이 문서에 있다」 까지만 알고
**어느 고침이 나빴는지** 모른다.

그래서 글이 들어오는 길을 **하나씩 다 찔러 봤다.**

| 길 | 막나 |
|---|---|
| `set_text` (문단) | 쓰기에서 |
| `set_text` (칸) | 쓰기에서 |
| `replace` | 쓰기에서 |
| `compose` — 본문·표 칸·제목·개조식·머리말 | 쓰기에서 |

여덟 길 다 XML 이 안 더러워진다. `compose` 는 **어느 블록의 어느 자리**인지까지 짚는다.

    blocks[2].rows[1][1] 의 1번째 글자 U+0000 는 XML 이 못 쓰는 제어문자다

**막는 자리는 글이 들어오는 길목마다 있어야 한다.** 한 곳만 막으면
막았다고 믿는 동안 딴 길로 샌다.

## 18. 글자 꾸밈은 **끄는 방법이 저마다 다르다**

HTML 로 옮기려고 `hh:charPr` 을 읽다가 문서 한 장을 통째로 못 쓰게 만들었다.

| 꾸밈 | 켜졌는지 보는 법 | 안 켜졌을 때 |
|---|---|---|
| 굵게 `hh:bold` | **요소가 있으면 켜진 것** | 요소가 없다 |
| 기울임 `hh:italic` | **요소가 있으면 켜진 것** | 요소가 없다 |
| 밑줄 `hh:underline` | `@type` 이 `NONE` 이 아니면 | 요소는 있고 `type="NONE"` |
| 취소선 `hh:strikeout` | **`@shape`** 가 `NONE`·`3D` 가 아니면 | 요소는 있고 `shape="NONE"` 또는 `"3D"` |

### 어떻게 알았나

취소선을 「요소가 있으면 켜진 것」으로 읽었다. 굵게가 그러니 같겠거니 했다.
계획서를 HTML 로 뽑아 PDF 로 구워 보니 **모든 글자에 줄이 그어져 있었다.**

`@type` 을 봤더니 늘 `undefined` 였다 — 취소선은 `@type` 이 아니라 **`@shape`** 다.

`shape="NONE"` 만 걸러도 모자랐다. 표본에서 세니 —

| 값 | 수 |
|---|---|
| `NONE` | 1524 |
| **`3D`** | **833** |
| `SOLID` | 2 |

교육부 업무계획은 `charPr` 125개 가운데 **124개가 `3D`** 였다.

## 20. 그리기 개체의 **음수 자리가 부호 없는 32비트**로 적혀 있다

`hp:offset/@y` 에 `4294955572` 가 들어 있었다.

    2³² − 4294955572 = 11724      →  진짜 값은 **−11724**

그대로 읽었더니 `top: 15377783mm`(15km)짜리 자리가 생겨,

## 21. 묶은 개체는 **개체마다 배율이 다르다**

「제목 띠」(배경 그림 + 글상자를 묶은 것)를 HTML 로 옮기며,
묶음이 줄어든 만큼 안의 것을 다 줄였다. 띠 제목 글자가 작아졌다.
한글 PDF 에서 그 글자를 재니 **15pt 그대로**였다 — 안 줄인 것이다.

값을 늘어놓으면 배율이 셋이다.

| | | |
|---|---|---|
| 묶음 | `orgSz` 28483 → `curSz` 21939 | **0.7702** — 자식의 **자리**를 옮기는 배율 |
| 그림 | `curSz` 37203 × **0.58971** = 21939 | 띠 크기에 꽉 맞춘다 |
| 글상자 | `curSz` 17503 × **1.026403** = 17966 | 거의 그대로 둔다 |

`0.58971` · `1.026403` 은 한글이 개체마다 **`hp:renderingInfo` 의
맨 뒤 `hc:scaMatrix`** 에 적어 둔 값이다.

### 규칙

- 자식의 **자리**: `hp:offset` × (묶음 `curSz` / 묶음 `orgSz`)
- 자식의 **크기**: 제 `curSz` × (제 마지막 `hc:scaMatrix` 의 `e1`·`e5`)

셈해서 맞히려 들지 말고 **적힌 것을 읽는다.**

### 왜 중요한가

묶음을 통째로 건너뛰면 **절 제목이 통째로 사라진다.**
계획서에서 「추진 개요」·「세부 추진 내용」·「예산 집행 계획」·「기대 효과」
넷이 다 빠졌는데, 도구는 아무 탈도 안 냈다.

## 24. 그러데이션 — 규격의 `Step` 범위가 실물과 다르다

`hc:gradation` 은 대화상자와 하나씩 맞물린다.

| 대화상자 | 속성 | 규격이 말하는 값 |
|---|---|---|
| 유형 | `@type` | `Linear` · `Radial` · `Conical` · `Square` |
| 기울임(시작각) | `@angle` | 기본 90 |
| 가로·세로 중심 | `@centerX` `@centerY` | 기본 0 |
| 번짐 정도 | `@step` | **규격은 0~100** |
| 번짐 중심 | `@stepCenter` | 0~100, 기본 50 |
| 색 수 | `@colorNum` | 늘 2 |

### 규격이 틀렸다

`@step` 을 실제 문서에서 재니 **`50` 과 `255`** 가 나온다.
규격 문서는 `0 ~ 100` 이라고 적어 놓았다. **255 는 그 범위 밖이다.**

규격을 믿고 0~100 로 눌러 담으면 어긋난다. 실물이 이긴다.

### 각도

한글 `angle=90` 이 대화상자의 「세로」다. CSS `linear-gradient` 는
`180deg` 가 위→아래(세로)라 **90을 더해서** 옮긴다.

    한글 angle 90 (세로)  →  CSS 180deg
    한글 angle  0 (가로)  →  CSS  90deg

띠가 단색으로 나오면 그러데이션을 못 읽은 것이다.

## 25. `colAddr` 은 **절대 열 번호**다 — 덮인 자리를 건너뛴다

칸(열)을 넣고 빼는 것을 만들면서 두 번 걸렸다.

### 하나 — 0,1,2… 로 다시 매기면 안 된다

표에서 셀들의 `colAddr` 을 왼쪽부터 0,1,2… 로 매기면 될 것 같다. 아니다.
**위 줄에서 세로로 덮은 자리는 그 줄에 셀이 아예 없다.**

    줄3: col0(×1/3) col1 col2(×1/3) col3(×1/3) col4(×1/3) col5 col6
    줄4: col1                                            col5 col6
                    ↑ 0·2·3·4 는 위가 덮었다 — 셀이 없다

0,1,2 로 매기면 줄4 가 `col0 col1 col2` 가 되어 **통째로 왼쪽으로 밀린다.**

그래서 자리표를 만들어 놓고 **빈 자리에만** 셀을 앉혀야 한다 —
`rowSpan` 을 만나면 아래 줄의 그 칸들을 미리 막아 둔다.

### 둘 — `colCnt = 칸수` 는 제자리를 맴돈다

`칸수` 는 `hp:tbl/@colCnt` 를 **읽는** 것이다. 그래서

    setAttr(this.el, 'colCnt', String(this.칸수));   // 아무것도 안 바뀐다

칸을 지워도 수가 안 줄어, 폭을 다시 나눌 때
**「열이 3개인데 폭을 2개 줬다」** 로 걸렸다.
격자를 훑어 **실제로 몇 칸인지** 세서 넣어야 한다.

### 다시 재는 법

    npx vitest run packages/doc/test/표.test.ts

「세로로 덮인 자리를 건너뛰고 주소를 매긴다」 가 그것을 본다.
합침을 만들어 두고 칸을 넣은 뒤 줄마다 주소를 확인한다.

### 칸을 넣을 때 표 폭

새 칸에 이웃 폭을 그대로 주면 **표가 그만큼 넓어져 쪽 밖으로 나간다.**
양식은 폭이 정해진 것이라, 있던 폭을 줄여 자리를 낸다 — 총폭을 지킨다.

## 26. 선을 지우는 것은 **굵기가 아니라 종류**다

표에서 세로선만 걷어내려고 굵기를 `0 mm` 로 줬다. **격자가 그대로 나왔다.**

표본 9편의 테두리 면 **3,603개**를 세어 봤다.

| 굵기 | 몇 번 |
|---|---|
| `0.12 mm` | 2043 |
| `0.1 mm` | 607 |
| `0.4 mm` | 443 |
| `0.5 mm` | 171 |
| … | |

**`0 mm` 는 한 번도 안 나온다.** 가장 가는 것이 `0.1 mm` 다.
한글은 0 을 받으면 가장 가는 값으로 올려 놓고 그린다.

그러면 한글은 선을 어떻게 지우나 — `type="NONE"` 을 쓴다(1,332번).
그리고 **그 면들도 굵기를 그대로 들고 있다.**

| `type="NONE"` 인 면이 든 굵기 | 몇 번 |
|---|---|
| `0.12 mm` | 646 |
| `0.1 mm` | 484 |
| `0.4 mm` | 95 |

굵기는 **껐을 때를 위해 남겨 두는 값**이지 스위치가 아니다.
다시 켜면 그 굵기로 돌아온다.

    <hh:leftBorder type="NONE" width="0.12 mm" color="#000000"/>
              ↑ 이게 스위치        ↑ 이건 꺼 둔 동안에도 남는 값

그래서 `border_width: 'none'` · `cells[].left: 'none'` 은 **종류를 NONE 으로**
바꾼다. 굵기는 `0.1 mm` 를 넣어 둔다 — 0 을 넣어 봐야 한글이 되돌린다.

### 다시 재는 법

    py -3 - <<'EOF'
    import zipfile, re, os, collections
    굵기 = collections.Counter(); 종류 = collections.Counter()
    for 갈, _, 파일들 in os.walk('자료/표본'):
        for f in 파일들:
            if not f.lower().endswith('.hwpx'): continue
            with zipfile.ZipFile(os.path.join(갈, f)) as z:
                for n in z.namelist():
                    if not n.endswith('.xml'): continue
                    x = z.read(n).decode('utf-8', 'replace')
                    for m in re.finditer(r'<hh:(?:left|right|top|bottom)Border[^>]*>', x):
                        w = re.search(r'width="([^"]*)"', m.group(0))
                        t = re.search(r'type="([^"]*)"', m.group(0))
                        if w: 굵기[w.group(1)] += 1
                        if t: 종류[t.group(1)] += 1
    print(굵기.most_common(10)); print(종류.most_common())
    EOF

## 27. ID 는 **연 문서 안에서만** 산다 — 저장하고 다시 열면 밀린다

`식별자.ts` 머리말에 「앞에 무엇을 넣든 객체는 그대로다 — 그래서 ID 가 안 밀린다」
고 적어 뒀다. **반만 참이었다.**

열쇠는 노드 객체라 문서를 들고 있는 동안에는 참이다. 그런데 ID **값**은
`다음번호++` 로, **문서를 훑는 차례**에서 나온다. 저장하고 다시 열면 다시 훑는다.
구조가 달라졌으면 같은 요소가 딴 번호를 받는다.

### 표는 문단 **다음에** 매긴다 — 그래서 통째로 밀린다

    for (const p of s.모든문단들) { 아이디(p.el); }   // ← 문단 먼저
    for (const t of s.표들)      { 아이디(t); }       // ← 표는 그 다음

줄을 하나 넣으면 칸마다 문단이 생긴다. 문단 수가 늘면 표 번호가 통째로 밀린다.
**고친 표만이 아니라 그 문서의 표가 전부다.**

줄 하나를 넣고 저장했다 다시 열었을 때 —

| 문서 | 표 | 문단 | 밀린 표 ID | 밀린 문단 ID |
|---|---|---|---|---|
| 교육부-대학혁신지원사업-기본계획 | 65 | 1035 → 1039 | **65** | 0 |
| 교육부-대학혁신지원사업-보도자료 | 5 | 85 → 88 | **5** | 0 |
| 교육부-업무계획 | 13 | 500 → 503 | **13** | 0 |
| 교육부-전문대학혁신지원사업 | 64 | 1053 → 1054 | **64** | 0 |
| 구역여럿-검인정도서매뉴얼 | 27 | 920 → 924 | **27** | **8** |
| 그림많음-돌봄교실계획 | 39 | 798 → 823 | **39** | 0 |

문단 ID 는 대개 안 밀린다 — 새 문단이 훑는 차례의 **뒤쪽**에 붙기 때문이다.
다만 **구역이 여럿이면 뒤 구역의 문단 ID 가 밀린다**(검인정도서매뉴얼 8개).
구역마다 「문단 다 → 표 다」 를 되풀이하므로, 앞 구역이 늘면 뒤 구역이 밀린다.

### 무엇이 밀리고 무엇이 안 밀리나

| | 연 채로 | 저장 → 다시 열기 |
|---|---|---|
| `set_text`·`replace`·`set_style` | 그대로 | **그대로** |
| `insert_row`·`insert_col`·`merge_cells` … | 그대로 | **표 ID 전부 밀림** |
| 손 안 댐 | 그대로 | 그대로 |

### 어떻게 알았나

아래로 쓰는 앱(Draftsmith)이 `set_table` 을 재려고 줄을 넣고 저장한 뒤,
저장 전에 받아 둔 `tbl_icyc` 로 다시 연 문서를 가리키다 **셋 다 자빠졌다.**
그쪽이 갈라 재서 알려 줬고, 이쪽에서 표본으로 다시 재니 **한 표가 아니라
전부**였다.

그쪽 지침에는 「문단·표 id 는 줄을 넣어도 그대로다」 라고 적혀 있었다.
**연 채로는 맞아서 반만 참인 문장**이었다 — 이쪽 주석과 똑같이.

### 그래서 어떻게 했나

고치지 않고 **드러냈다.** ID 를 파일에 적어 두면 문서를 건드리게 되고,
내용에서 뽑으면 같은 글이 여럿일 때 겹친다.

- `save_document` 가 `ids_stale: true` 로 알린다. 말로도 적는다.
- `식별자.test.ts` 가 이 성질을 못 박는다 — 다음에 또 어긋나면 시험이 깨진다.

    npx vitest run packages/doc/test/식별자.test.ts
